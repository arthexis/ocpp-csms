## External and dynamic consumers — not a closed world

- **Reports:** `arthexis/ocpp-reports/src/ocpp_reports/active_csms.py:39-85` executes `python -c` imports of `ocpp_csms.cli.cli_data_dir`, `ocpp_csms.export_contract.export_contract` and `ocpp_csms.transaction_soc.transaction_soc` with the *active CSMS interpreter*. `follow.py` imports export code lazily. `csms_wal_reader.py:34-45` and `source_activation_plan.py:18-53` rely on read-only SQLite/WAL, source identity and v8 layout. Reports is not a reason to grant CSMS database write access.
- **GWay Remote:** `arthexis/gway-remote/gway_remote/csms_health.py:19-55` calls `ocpp-csms status --json`, validating `ocpp-csms/status/v1`; `mobile.py:25-45` invokes historical CLI grammar. Exit codes, keys, installed executable and defaults matter.
- **OCPP Simulator:** `arthexis/ocpp-simulator/go/internal/spike/recovery_csms_v8_observation.go:63-68,102-135` reads disposable v8 evidence for offline observation only. It must not infer StopTransaction, recovery permission or ownership from status.
- **Discover/Ansible:** `ocpp_discover/first_contact.py` imports `ocpp_csms.schema.DATABASE_FILENAME` and uses SQLite read-only; deployment scripts inspect version and installed command/service shape.
- **Dynamic imports:** Searching ordinary `import ...` statements inside CSMS does **not** cover subprocess Python snippets, `importlib.import_module`, external AgentOps payloads, private scripts and field-installed tooling. Previous scoped source survey reported no internal dynamically named CSMS imports, but that is **not** universal absence proof. The new tests exercise known legacy module names via `importlib`, not an invented plugin framework.
